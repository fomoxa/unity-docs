## 1. Ports and services

What the client sees:

| Port on your machine | Protocol | Goes to | Purpose |
|---|---|---|---|
| 9600 | TCP | `backend` | login, rooms, friends, scores (fRPC) |
| 7777 | UDP | `gateway` | gameplay |
| 9643 | TCP | `tls-proxy`, then `backend:9600` | the same as 9600 but TLS-encrypted (optional, recommended outside your own network) |
| 7350 | TCP | `nakama` | test scripts only. The client does not use it |

Inside the cluster (namespace `fomoxa`), the client never connects directly:

| Component | Service type | Ports | Who connects | Image or source |
|---|---|---|---|---|
| `postgres` | ClusterIP | 5432 | nakama | `postgres:15` |
| `nakama` | LoadBalancer | 7350 (API) | backend, test scripts | `registry.heroiclabs.com/heroiclabs/nakama:3.41.0` |
| `nakama-console` | ClusterIP | 7351 | you, through `port-forward` | (the nakama pod) |
| `directory` | ClusterIP | 9500 (pods, backend, gateway), 9501 (admin) | game servers, backend, gateway | `fomoxa-directory` (Rust) |
| `gateway` | LoadBalancer | 7777/UDP | client | `fomoxa-gateway` (Rust) |
| `backend` | LoadBalancer | 9600 (players), 9601 (WebSocket) | client, tls-proxy | `fomoxa-backend` (.NET) |
| `backend-pods` | ClusterIP | 9602 | game servers reporting counts and scores | (the backend pod) |
| `tls-proxy` | LoadBalancer | 9643 | client | `nginxinc/nginx-unprivileged:1.27-alpine` |
| game server (Agones Fleet) | (pod, port 7778/UDP) | 7778 | gateway | `fomoxa-server` (.NET) |

Metrics ports (Prometheus only): backend 9610, game server 9611, Nakama 9100.

Other namespaces: `agones-system` (Agones) and `monitoring` (optional).

## 2. Directory and gateway settings

### `directory.toml` (in the ConfigMap `directory-config`, file `deploy/k8s/directory.yaml`)

```toml
listen = "0.0.0.0:9500"            # pods, backend and gateway connect here
admin_listen = "0.0.0.0:9501"      # admin (drain, read the pod list)

public_address = "127.0.0.1:7777"  # the GATEWAY address the CLIENT sees

grace_seconds = 30                 # how long a silent pod stays before it is treated as dead
report_interval_seconds = 5        # how often pods report load
drain_seconds = 300                # the longest a pod may take to drain
ticket_seconds = 30                # how long a room ticket lives

[keys]                             # keys by role, read from the secret mounted at /secrets/directory/
backend = { file = "/secrets/directory/backend" }
pod     = { file = "/secrets/directory/pod" }
gateway = { file = "/secrets/directory/gateway" }
admin   = { file = "/secrets/directory/admin" }
root    = { file = "/secrets/directory/root" }

[[placement]]
filter = "pod.version == client.version"     # only pair pods that run the client's version

[[placement]]
prefer = "pod.region == client.region"       # prefer the same region
weight = 10

[[placement]]
sort = "packed"                              # fill pods that already have players first
```

| Setting | Meaning | Constraint |
|---|---|---|
| `public_address` | With a gateway in front, `Allocate` returns this address instead of the pod's real one. It must be a UDP address the client can reach | local: `127.0.0.1:7777`; see [05, section 14](operations/05-scaling-security-backup.md#14-changing-the-public-address-publicaddress) |
| `drain_seconds` | The longest a pod may wait for players to leave while draining | the Fleet's `terminationGracePeriodSeconds` (360) must be larger |
| `[keys].root` | the root key | exactly 64 hex characters (32 bytes); the other keys are at least 16 bytes |

### `gateway.toml` (ConfigMap `gateway-config`, file `deploy/k8s/gateway.yaml`)

```toml
listen = "0.0.0.0:7777"                                 # UDP, the only entry point for game servers
pod_bind = "0.0.0.0:0"                                  # source port the gateway uses to talk to pods
directory = "directory.fomoxa.svc.cluster.local:9500"   # a DNS name inside the cluster
retry_seconds = 1

[keys]
gateway = { file = "/secrets/directory/gateway" }       # the gateway needs only its own key
```

After editing a ConfigMap, run `kubectl rollout restart deployment/<directory|gateway> -n fomoxa` so it reads the new value.

## 3. Secrets

Generated by `scripts/gen-keys.sh` and `scripts/gen-tls-cert.sh` (expanded in [03, Step 2](deploy/01-prepare-and-keys.md#step-2-generate-keys-and-the-certificate)) and loaded into the cluster by `scripts/gen-k8s-secrets.sh` ([Step 8](deploy/04-secrets.md#step-8-namespace-and-secrets)).

Files in `deploy/secrets/` (never committed):

| File | Hex length | Used for |
|---|---|---|
| `directory/root` | 64 | the directory's root key |
| `directory/admin` | 48 | directory administration |
| `directory/backend` | 48 | backend to directory |
| `directory/gateway` | 48 | gateway to directory |
| `directory/pod` | 48 | game server to directory |
| `backend-pod` | 48 | game server to backend (port 9602) |
| `nakama/server-key` | 32 | the application's login to Nakama |
| `nakama/http-key` | 48 | the backend's calls to Nakama's internal RPCs |
| `nakama/console-password` | 32 | the Nakama console |
| `nakama/session-key`, `nakama/refresh-key` | 48 | encrypt Nakama tokens |
| `nakama/db-password` | 32 | the Postgres password |
| `tls/tls.crt`, `tls/tls.key` | (PEM) | the `tls-proxy` certificate |

Secrets in the cluster (namespace `fomoxa`) and which pod sees what:

| Secret | Holds | Mounted or read by |
|---|---|---|
| `fomoxa-directory-keys` | backend, pod, gateway, admin, root | `directory` (all five); `gateway` mounts only the `gateway` key |
| `fomoxa-backend-keys` | backend, backend-pod | `backend` |
| `fomoxa-pod-key` | pod | game servers |
| `fomoxa-backend-pod-key` | backend-pod | game servers (kept separate, without the backend-to-directory key) |
| `fomoxa-nakama` | six Nakama and Postgres values | `nakama`, `postgres`, `backend` |
| `fomoxa-tls` | `tls.crt`, `tls.key` | `tls-proxy` |
| `grafana-admin` (namespace `monitoring`) | password | `grafana` |

## 4. Scripts and their manual equivalents

Every script is a shortcut. The table shows what each one actually runs, and where the manual version is.

| Script | What it does (expanded) | Manual commands in |
|---|---|---|
| `scripts/gen-keys.sh [-f]` | for each file: `openssl rand -hex N \| tr -d '\n' > file` (12 keys); skips files that exist unless `-f` | [03, Step 2](deploy/01-prepare-and-keys.md#step-2-generate-keys-and-the-certificate) |
| `scripts/gen-tls-cert.sh [-f]` | `openssl req -x509 -newkey rsa:2048 -nodes -days 730 -keyout tls.key -out tls.crt -subj "/CN=$TLS_HOST" -addext "subjectAltName=..."`, then prints `openssl x509 -outform DER \| openssl dgst -sha256 -hex` (the pin) | [03, Step 2](deploy/01-prepare-and-keys.md#step-2-generate-keys-and-the-certificate) |
| `scripts/gen-k8s-secrets.sh [ns]` | calls `gen-keys.sh` if keys are missing; six `kubectl create secret ... --dry-run=client -o yaml \| kubectl apply -f -` commands | [03, Step 8](deploy/04-secrets.md#step-8-namespace-and-secrets) |
| `scripts/build-images.sh [tag]` | `git clone -b 0.2.0 .../gateway` if missing; four `docker build -f ... -t fomoxa-*:tag` commands | [03, Steps 3 and 4](deploy/02-build-images.md#step-3-get-the-gateway-rust-source) |
| `scripts/k8s-up.sh [--build]` | checks `docker info` and installs k3d and helm if missing, checks ports, `k3d cluster create fomoxa --port ...@loadbalancer`, `helm repo add` and `helm install agones ...`, (`--build`: `build-images.sh`), `k3d image import`, `kubectl apply` for the namespace and `gen-k8s-secrets.sh`, `kubectl apply` for 7 manifests, `kubectl rollout status` | [03, the whole document](deploy/README.md#one-command-shortcut) |
| `scripts/k8s-down.sh [--keep-cluster]` | `kubectl delete namespace fomoxa` (with `--keep-cluster`) or `k3d cluster delete fomoxa` | [03, Step 14](deploy/08-test-client-and-cleanup.md#step-14-clean-up) |
| `scripts/test-nakama.sh`, `test-nakama-pool.sh` | `curl` against Nakama: device login, `reset_match`, `find_match` twice, `poll_match`, `verify_ticket`; keys come from `lib-nakama-keys.sh` | [03, Step 12](deploy/07-test-nakama.md#step-12-test-nakama-with-curl), [06, section 3](testing.md#3-the-nakama-lua-module) |
| `scripts/lib-nakama-keys.sh` | (sourced) if port 7350 belongs to a `k3d-*` container, reads `server-key` and `http-key` from the secret `fomoxa-nakama`; otherwise uses compose's default keys | [05, section 9](operations/03-tls-and-keys.md#9-nakama-keys-and-passwords) |
| `scripts/test-p5.sh [room1 room2]` | `kubectl get gs`, then calls `powershell.exe test-p5.ps1` (four `MyGame.exe -autojoin` clients) with `FOMOXA_KUBECTL_WSL=1`, and checks exactly 2 `Allocated` pods | [03, Step 13](deploy/08-test-client-and-cleanup.md#step-13-test-with-the-unity-client-real-players) |
| `scripts/run-mock-cluster.sh [options]` | `dotnet publish` of the game server and MockCluster into `.mock/`, then `dotnet .mock/cluster/MockCluster.dll --server=... [options]` | [02, Steps 1 and 2](getting-started/quickstart-mock-cluster.md) |
| `scripts/test-real-backend.sh` | `docker compose up -d`, three `dotnet publish` commands, the backend with `Fomoxa__*` variables, `MockCluster --selftest-target=9600,9602 --selftest`, `curl /metrics`, cleanup | [06, section 4](testing.md#4-real-backend-with-real-nakama) |
| `scripts/stop-all.sh` | `pkill -9 -f` for processes named `fomoxa-directory`, `fomoxa-gateway`, `MyGame.Server`, `MyGame.Backend` and `MyGame` (and `taskkill.exe` on Windows); for the setup without Kubernetes | none |

PowerShell versions (`.ps1`) for Windows: `gen-keys.ps1`, `gen-tls-cert.ps1`, `gen-k8s-secrets.ps1`, `build-images.ps1`, `k8s-up.ps1`, `k8s-down.ps1`, `test-nakama.ps1`, `test-nakama-pool.ps1`, `test-p5.ps1` and `run-mock-cluster.ps1` do the same as their `.sh` counterparts.

The older Windows setup, with no Kubernetes (the Rust directory and gateway built as `.exe` and run directly), uses `start-cluster.ps1` (starts a whole local cluster), `run-directory.ps1`, `run-backend.ps1`, `run-pod.ps1`, `run-client.ps1`, `stop-all.ps1`, and the tests `test-p4.ps1` and `test-console-server.ps1`. These documents do not use them, because the mock cluster ([02](getting-started/quickstart-mock-cluster.md)) can replace them without building Rust.

`scripts/sync-server-deps.ps1` (Windows) copies the source of the two Fomoxa packages from `MyGame/Library/PackageCache/` into `server-deps/`, so the console game server builds without Unity. Rerun it every time you change a package version in `MyGame/Packages/manifest.json`, after Unity has downloaded the packages.

## 5. Environment variables and flags

### Game server `MyGame.Server`

Priority order: the command-line flag `--name=value`, then the environment variable, then the default.

| Flag | Environment variable | Default | Meaning |
|---|---|---|---|
| `--directory` | `FOMOXA_DIRECTORY` | `127.0.0.1:9500` | directory address |
| `--name` | `FOMOXA_POD_NAME` | `pod-1` | pod name (registered with the directory) |
| `--address` | `FOMOXA_POD_ADDRESS` (or `POD_IP`) | `127.0.0.1` | IP the pod reports to the directory |
| `--port` | `FOMOXA_POD_PORT` | 7778 | UDP port |
| `--version` | `FOMOXA_VERSION` | `1.0` | version; only clients of this version are paired |
| `--region` | `FOMOXA_REGION` | `local` | region |
| `--max-players` | `FOMOXA_MAX_PLAYERS` | 16 | capacity of one pod |
| `--room` | `FOMOXA_ROOM` | `arena:1` | list of rooms, comma separated |
| `--claim-one` | `FOMOXA_CLAIM_ONE` | false | each pod claims only one free room from the list (used with a Fleet) |
| `--behind-gateway` | `FOMOXA_BEHIND_GATEWAY` | true | the pod sits behind a gateway (false: clients connect to the pod directly, as in the mock cluster) |
| `--agones` | `FOMOXA_AGONES` | on when `AGONES_SDK_GRPC_PORT` is set | report state to the Agones sidecar |
| `--key` | `POD_KEY_FILE` | required | the file with the `pod` key |
| `--backend` | `FOMOXA_BACKEND` | empty (off) | the backend's `host:9602`, for reporting counts and scores |
| `--backend-key` | `POD_BACKEND_KEY_FILE` | | the file with the `backend-pod` key (required with `--backend`) |
| `--metrics` | `FOMOXA_METRICS` | empty (off) | `host:port` for the HTTP `/metrics` (Kubernetes: `0.0.0.0:9611`) |
| `--trace` | `FOMOXA_TRACE` | false | print player positions every two seconds |

### Backend (`MyGame.Backend`)

.NET settings have the form `Fomoxa:Section:Key`. As environment variables, replace `:` with `__`.

| Variable | Default | Meaning |
|---|---|---|
| `Fomoxa__Directory__Address` | `127.0.0.1:9500` | the directory |
| `Fomoxa__Directory__Key__File` | required | the file with the `backend` key |
| `Fomoxa__Players__Tcp` and `Fomoxa__Players__WebSocket` | `0.0.0.0:9600` and `0.0.0.0:9601` | player ports (set WebSocket to `""` to turn it off) |
| `Fomoxa__Pods__Tcp` and `Fomoxa__Pods__Key__File` | `0.0.0.0:9602` and required | the pod port, and the file with the `backend-pod` key (at least 16 bytes) |
| `Fomoxa__Nakama__Url` | empty | the Nakama URL. Empty means no Nakama: instant matchmaking and in-memory accounts |
| `Fomoxa__Nakama__ServerKey` and `HttpKey` | `defaultkey` and `defaulthttpkey` | the Nakama keys (Kubernetes takes them from the secret) |
| `Fomoxa__Data__File` | empty | a JSON file for accounts when there is no Nakama |
| `Fomoxa__Metrics__Listen` | `0.0.0.0:9610` | the HTTP `/metrics` address (empty turns it off) |

Command-line flags are in the table in [04, Step 5](unity-client.md#step-5-run-the-build-and-use-the-flags).

## 7. Backend RPC interface

fRPC over TCP 9600. The source of truth is `MyGame.Backend/MyGame.Backend/Services.cs`, with the models in `Models/*.cs`.

`Players.Login(PlayerLogin) -> PlayerWelcome` is the authentication step when connecting. The `PlayerLogin.Mode` values:

| `Mode` | Does | Fields used |
|---|---|---|
| `register` | creates an account | `Player`, `Secret` = the password |
| `login` | logs in | `Player`, `Secret` |
| `recover` | resets the password | `Player`, `Recovery` = the recovery code, `Secret` = the NEW password |
| (empty, no `Secret`) | guest, or the older style | `DeviceId` (through Nakama), or just `Player` (a backend with no Nakama) |

`Lobby` (login required): `ListRooms`, `JoinRoom(RoomKey, Version) -> RoomTicket`, `Presence(Room) -> OnlineList`, `TakeRecoveryCode`, `ChangePassword`, `GetProfile`, `Social`, `FriendAction(request|accept|decline|remove|dismiss-invite)`, `Invite`, `Scoreboard(Room)`.

`PodGate` (the `backend-pod` key): `ReportRoom(RoomKey, Players, Capacity)`, `ReportScores(Room, [Player, Steps])`, `TransferPlayer` (unused).

`Directory` (backend, pod and gateway to the directory, port 9500): `Allocate`, `RegisterPod`, `AcquireRoom`, `ReleaseRoom`, `ReportLoad`, `WatchDrain`, `RequestDrain`, `WatchPods`. `DirectoryAdmin` (the `admin` key, port 9501): `Drain`, `ReadPods`.

## 8. Gameplay constants

Defined once, in `MyGame/Assets/Network/Models/Course.cs`, and shared by the Unity client and the server.

| Constant | Value | Meaning |
|---|---|---|
| `Count` | 18 | number of platforms |
| `StepHeight` | 1.4 m | platform *n* has its top at *n* x 1.4 m |
| `PlatformHalf` | 1.75 m | half the side of a platform (a 3.5 m square) |
| `Radius`, `AngleStepDegrees` | 7 m, 40 degrees | the platforms spiral around the center of the floor |
| `Speed` | 6 m/s | running speed |
| `Gravity`, `JumpSpeed` | 25 m/s^2, 9.5 m/s | maximum jump height is about 1.8 m, enough to clear one 1.4 m step |
| `Bounds` | 23 m | edge of the play area |
| `PlayerRadius`, `PlayerHeight` | 0.5 m, 2 m | character size |

To change a constant, edit that one file and rebuild both the client and the game server. The scene rebuilds its platforms when you run Rebuild Scene.
